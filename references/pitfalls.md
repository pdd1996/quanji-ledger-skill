# 已知的坑（全部为实测，含可复现的数字）

## 一、官方统计口径本身有 3 个坑 —— 不要拿它当校验真值

支付宝 preamble 自己写着：
> "6.因统计逻辑不同，明细金额直接累加后，可能会和下方统计金额不一致，**请以实际交易金额为准**。"

> 📌 本文所有金额都是**为讲清口径而构造的示例值**，不是任何真实账单的数字。
> 它们只保证"算式自洽"，不要拿去和你的账本比对。

### 坑 1：同一行统计里，笔数和金额口径不一致

```
官方「支出：120 笔 10000.00 元」（虚构示例值）
  笔数 120     = 全部支出行 120 笔（含「交易关闭」10 笔 + 零金额 2 笔）
  金额 10000.00 = 支出总额 12000.00 − 交易关闭部分 2000.00
```

**笔数含"交易关闭"，金额不含。** 所以想复现官方数字，必须对笔数/金额用两套规则。

**补充实测（容易踩的更细一层）：只扣「支出桶」里的交易关闭，收入桶里的不扣。**

退款流水里存在 `收/支 = 收入`、`交易状态 = 交易关闭` 的行。官方的支出金额
**没有**把这笔从支出里扣掉 —— 它压根不在支出桶里。如果图省事写成
"支出 = 全部支出行 − 全部交易关闭行"，会**少算**这一笔（实测偏差正好等于该笔金额）。

> 正确写法：只减去 `direction == "expense"` 且状态为关闭的行。
> 这就是为什么对账脚本要区分"支出桶关闭"和"关闭总数"。

### 坑 2：不计收支的差额是"桶内冲减"

```
全部不计收支行合计 = 合计A（假设 12,000.00）
官方              = 合计B（假设 11,000.00）
差 = 1,000.00  ← 应正好等于「基金买入退款」几笔之和（假设 500 + 500）

（这里所有数字都是构造的示例：真实差额取决于当时的退款笔数与金额。）
```

规则：
- **基金买入退款**：原「买入」也在不计收支桶里 → 退款必须在**桶内冲减**
- **消费类退款**（例如购物类、票务类各若干笔）：原支出在「支出」桶里 →
  跨桶抵消，所以**保留在不计收支里**

### 坑 3：微信的统计是干净的

```
官方：支出 120 笔 10000.00 / 收入 5 笔 2000.00 / 中性 1 笔 30.00  → 与明细逐项一致（虚构示例值）
```

微信账单没有「交易关闭」和零金额，所以笔数金额都直接对得上。

### 坑 4：工行的逐页脚注是干净的，但只在"页内"成立

```
每页页脚：本页支出算术合计 / 本页收入算术合计 / 本页交易笔数
```

实测逐页与明细重算**差额全部为 0**，可以直接当校验基准。
但要注意 **跨页的配对交易会被拆到两页**（如「跨境汇款 -500」在第 10 页、
「他行汇入 +500」在第 11 页）—— 所以**不能拿单页脚注去核对单页的收入笔数含义**，
也不要用它推"这一天净流入了多少"。逐页核对金额与笔数即可。

### 正确的校验方式

**以明细为准**，用"还原官方口径"来验证解析器，而不是把官方数字当 ground truth：

```python
# 支付宝支出：笔数用全部支出行，金额排除交易关闭
n_exp = len([t for t in txns if t.direction == "expense"])
amt_exp = sum(t.amount for t in txns if t.direction == "expense" and t.status not in CLOSED)
# 支付宝不计收支：笔数用全部不计收支行，金额减掉桶内「买入退款」
n_neu = len([t for t in txns if t.direction == "neutral"])
amt_neu = sum(t.amount for t in txns if t.direction == "neutral") - sum(
    t.amount for t in txns if t.direction == "neutral" and "买入退款" in t.description)
```

## 二、口径混淆：转账不是消费（最容易把产品做错）

实测某 3 个月账单：

```
「转账·人际」成为第一大"消费"类目，占全部支出约 45%
单月最严重：占该月全部支出约 39%
```

**若不拆分口径，该月"消费"会被虚报约 65%**（量级示意：4,181 → 6,887）。

> **必须把每一笔拆成四类：消费 / 转账 / 投资 / 还款。**
> 混在一起，「我这个月花了多少」这个问题在定义上就无解。

### 银行流水更狠：内部划转是"带符号的支出"

工行明细里的「理财」（买理财/基金）和「金融付款」（缴费型划扣）合计占**支出笔数的大多数**，
但它们只是**账户内部资金调拨** —— 钱从活期挪到理财，并没有花掉。

```
同一份 3 个月工行明细（**虚构示例值**，只保证算式自洽）：
  按符号算支出（错）  ¥24,000.00
  按口径算消费（对）  ¥ 1,600.00      ← 相差 15 倍
```

**陷阱在于：这些行的「收支」列看不出问题。** 微信/支付宝的中性行写的是 `/` / `不计收支`，
一眼能认出；但银行流水的调拨**本身就带正负号**（理财买入 `-10.00`、他行汇入 `+500.00`），
所以**任何"只看符号"的聚合都会算错**。

> 处理方式：输出里带一列 **`口径桶`**（计入 / 不计收支 / 零金额 / 已剔除），
> 下游一律按它聚合（见 `ledger-model.md` 第一节）。
> 并且 **`classify_all` 必须跑在 `partition` 之前** —— 分流要按类目判，不是按符号判。
> `scripts/test_ledger_rules.py` 就是为了防这条回归。

## 三、花呗：必须按权责发生制

实测某 3 个月：**信用消费（花呗/信用购）占真实消费约 38%**；
同期还款 3 期。

- 用花呗消费时**钱没出去**，现金流出发生在**下个月的还款日**
- 若按现金流记账：「这个月花了多少」永远是错的
- 正确做法：消费按**发生日**计入消费；还款标记为**负债偿还**，不计收支

## 四、其他必须处理的明细问题

| 问题 | 处理 |
|---|---|
| `交易关闭` | **剔除**（未完成的交易，官方金额统计也不含）|
| `退款成功` | 与原始支出**配对冲销**（实测成对出现，且原交易常为 `交易关闭`）|
| 金额 = 0 | 单列（实测是「医保支付(不含自费)」，有信息价值但不算支出）|
| 重复小额 | **必须聚合**：实测「投资理财」类目里绝大多数是每只基金每日 10.00 元定投 → 折叠成个位数分组 |
| 中性交易 | 微信 `收/支 = /`、支付宝 `不计收支` → 资金流水区，默认折叠 |

## 五、技术坑（踩过的）

| 坑 | 症状 | 正确做法 |
|---|---|---|
| **UID 当成序号** | `list`/`fetch` **静默返回空**，看起来像"邮件没附件" | `UID FETCH` 的响应里必须解析 `UID nnn`，`item[0]` 开头是**序号**不是 UID |
| **域名用子串判断** | `phish@icbc.com.cn.evil.com` 被判成可信发件人（可被利用的仿冒） | 域名的层级从右往左，只能 `dom == pat or dom.endswith("." + pat)` |
| **白名单漏了银行** | 工行历史明细邮件明明在收件箱，却"没有候选邮件" | 白名单要含 `webmaster@icbc.com.cn` 与域 `@icbc.com.cn`；工行也走邮件下发 |
| RFC2047 折行 | 附件名乱码 | 用 `decode_header`；**不要**先 `re.sub(r"\s+","")`，会把 `?=` 和 `=?` 粘成 `?==?` |
| GBK 当 latin-1 | 中文附件名乱码 | `fn.encode("latin-1").decode("gbk")` 兜底 |
| imaplib 非 ASCII 搜索 | `SEARCH` 报错 | 用 `SINCE` 做粗筛，**中文关键词在本地用 Python 过滤** |
| ZipCrypto vs AES | 判断错加密方式导致用错工具 | `compress_type == 99` 才是 AES；`flag_bits & 0x40` 是 PKWARE 强加密。**`flag_bits & 0x1` 不是 AES 标志**，标准 ZipCrypto 也会置位，别拿它误判 |
| 非交互环境提示密码 | 管道里 `getpass` **卡死** | 只在 `sys.stdin.isatty()` 时提示 |
| **沙箱只读目录解压失败** | 报"口令未知"，但口令其实是对的 | 解压要写到**可写目录**；`PermissionError` 必须与"口令错"分开报，别被 `except` 吞掉 |
| **工行 PDF 的 x/y 是反的** | 明细"全空"，或列整列错位、金额与余额互换 | `x0`=行、`y0`=列，且 `y0` 越小越靠右；列带必须按 y0 升序、与列头顺序**反向**配对 |
| **工行 PDF 行距 == 行内偏移** | 每页**恰好少 3 笔**，余额链出现 -20/-30 的差 | 别按 x 聚簇；用**带符号金额格**当行锚点（水印没有金额格）|
| **工行 PDF 用水印当锚点** | 中位行距算成 7.5（真值 18），整行被切碎 | 也不要拿「日期格」当锚点：水印里含 `2026-10-13` 这类日期戳 |
| **工行 PDF 的水印落在列带内** | 摘要变成 `2026-10-13`，类目被污染 | 归位后**按内容过滤**：金额 `^[+-][\d,]+\.\d{2}$`、余额 `^[\d,]+\.\d{2}$` |
| PDF 库选择 | `pypdf` 取文字会得到错位的一列 | 用 **PyMuPDF** 的 `get_text("words")` 拿坐标，`pdftotext`/`pypdf` 的阅读顺序在这份文件里没意义 |
| 改了脚本却不生效 | 反复得到互相矛盾的解析结果 | 清 `__pycache__/`；`inspect.getsource()` 确认跑的是哪一版 |
| **同一账单从两条路径进来** | 行数翻倍（zip 和它解出来的文件都被吃掉） | 合并层按「交易单号」去重即可覆盖；不要靠"跳过某些文件"来防 |

## 六、加密与口令（合规相关，必读）

- 两个平台的账单 zip 都是 **ZipCrypto**（不是 AES）
- **解压口令每次都变**，由平台经**另一条通道**下发：
  - 微信 → 【微信支付】公众号消息
  - 支付宝 → 申请页面显示
- **工商银行是另一回事**：PDF 的**打开口令**由用户导出时自己设置，不是平台下发的解压口令。
  它加密的是文件本身（`permissions == 0`），所以**没有"空口令"路径**，
  拿不到口令就只能回 App 重新导出一份。建议通过 `ICBC_PDF_PWD` 环境变量传入，避免进 shell 历史。
- **ZipCrypto 的已知明文攻击（bkcrack）在此无意义** —— 因为口令是 6 位纯数字，
  **口令空间只有 10^6**，可直接穷举（实测约 16,000 次/秒 ≈ 60 秒）。

> ⚠️ **默认不要主动穷举口令。** 这是产品级决策，涉及平台协议与商店审核风险。
> 与用户明确确认后再做，并说明代价。**服务端绝不接触口令。**
