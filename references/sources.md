# 微信 / 支付宝 / 工商银行 账单的真实来源与格式

> 全部来自真实导出文件的实测（实测年月已隐去 —— 账单导出的时间点本身属于个人信息），
> 不是文档推测。格式会随平台改版变化，
> **遇到解析失败先重新核对这些特征，不要假设用户给的是旧格式。**

## 一、取件路径

| 平台 | 邮件发件人 | 邮件里的文件 | 有效期 |
|---|---|---|---|
| 微信支付 | `wechatpay@tencent.com` | **没有附件** —— 正文里只有「点击下载」链接 | **链接 7 天过期** |
| 支付宝 | `service@mail.alipay.com` | **附件 `.zip`** + 正文里也有一个链接 | 附件长期 |
| 工商银行 | `webmaster@icbc.com.cn`（域 `icbc.com.cn`） | **附件 `.pdf`**（历史明细，带打开口令） | 附件长期 |

> 工行的历史明细也是**邮件下发**的，别只按「App 里下载」去理解取件路径。
> 但 `webmaster@icbc.com.cn` 是**综合发信口** —— 营销、安全提醒也走它，
> 所以白名单只决定"是否候选"，真正取件仍要**按附件类型过滤**（见第七节与 `harvest`）。

### 微信的下载链接（关键）

```
https://tenpay.wechatpay.cn/userroll/userbilldownload/downloadfilefromemail?encrypted_file_data=<token>
```

- 直接 GET 就返回 `Content-Type: application/zip`，无需 cookie / 登录
- `Content-Disposition` 里的 filename 是 **percent-encoded UTF-8**
- **同一链接可重复下载**（实测多次成功），但 **7 天后失效**
- 邮件原文提到："解压密码已通过【微信支付】公众号发送至申请人微信"

> ⚠️ **因此"用户导出后忘了下载"是真实高频损失** —— 自动取件的首要价值是赶在 7 天内把文件拿回来，
> 而不是省几次点击。

### 支付宝

- 附件名用**非标准的 RFC2047 + GB18030**，且**折行**（下面的日期是示例）：
  `=?GB18030?Q?=D6=A7=B8=B6...?=\r\n =?GB18030?Q?2-YYYYMMDD).zip?=`
- 必须用 `email.header.decode_header` 解码；**不要**先删掉折行空白，否则相邻 encoded-word
  会被粘成 `?==?` 破坏 token 化

## 二、容器与内容

| | 微信 | 支付宝 | 工商银行 |
|---|---|---|---|
| 外层 | ZipCrypto 加密 zip | ZipCrypto 加密 zip | **加密 PDF**（打开口令，非解压口令）|
| 内层 | **`.xlsx`** | **`.csv`（GBK）** | 无（表格直接画在页里）|
| 压缩 | DEFLATE（`compress_type=8`，不是 AES 的 99）| 同 | —— |
| 大小参考 | 约 10 KB | 约 17 KB | 数百 KB（页数 × 行数）|
| 表格形态 | 普通行列 | 普通行列 | **整页横排**，见第八节 |

> 工行那份 PDF 的 `/Perms` 是空的（`permissions == 0`），所以**只能靠口令打开**，
> 没有"空口令"可用。口令是导出时用户自己设的，通常 6 位。

## 三、表头前的 preamble（必须先跳过）

两个平台都在真正表头之前放了一段说明文字，且**列数不同、行数不同**。

- 微信：**17 行** preamble，单列纵向排布
- 支付宝：**23 行** preamble（含一条 `-----` 分隔线）

**定位表头的稳健方法**：找同时含 `交易时间` 且某列以 `金额` 开头的行。

### preamble 里的官方统计（可解析，但不可当校验真值）

```
微信：共39笔记录 / 收入：5笔 2000.00元 / 支出：33笔 4400.00元 / 中性交易：1笔 30.00元
支付宝：共530笔记录 / 收入：4笔 3800.00元 / 支出：120笔 10000.00元 / 不计收支：408笔 33000.00元
```

> 上面是**虚构示例值**（只保留真实的行数结构，金额已替换），仅用于说明 preamble 的格式。

## 五、值域（实测枚举）

**微信**
- `收/支`：`支出` | `收入` | `/`（中性）
- `交易类型`：商户消费 / 转账 / 微信红包 / 微信红包（群红包）/ 群收款 / 扫二维码付款 / 转入零钱通-来自零钱 / 其他
- `支付方式`：零钱 / 零钱通 / 各银行储蓄卡(尾号) / `/`
- `当前状态`：支付成功 / 对方已收钱 / 已存入零钱 / 已到账 / 已转账

**支付宝**
- `收/支`：`支出` | `收入` | **`不计收支`**
- `交易分类`：**19 类** —— 投资理财 / 交通出行 / 餐饮美食 / 日用百货 / 充值缴费 / 信用借还 /
  退款 / 转账红包 / 爱车养车 / 医疗健康 / 其他 / 数码电器 / 收入 / 商业服务 / 生活服务 /
  运动户外 / 家居家装 / 宠物 / 教育培训
- `收/付款方式`：各银行储蓄卡 / 余额宝 / **花呗** / 花呗&红包 / 账户余额 / 空
- `交易状态`：交易成功 / 退款成功 / 付款成功，基金份额确认中 / **交易关闭** / 还款成功 / 支付成功 / 等待确认收货

## 六、格式细节（会直接影响解析）

| 细节 | 说明 |
|---|---|
| 编码 | 支付宝 CSV 是 **GBK**；微信 XLSX 是二进制 |
| 金额 | 微信是**数字单元格**（int / float 混合）；支付宝是字符串 `10.00` |
| 字段内 TAB | 支付宝 `交易订单号` 后带 `\t`，**必须 strip** |
| 主键 | 微信 `交易单号`、支付宝 `交易订单号`，实测均 **100% 唯一** |
| 列数一致性 | 支付宝每行列数稳定为 13；商品说明里的逗号不会撑破列（无引号嵌套问题）|
| 零金额 | 存在金额 `0.00` 的行（医保支付），不能直接丢弃 |

## 七、发件人白名单

```
service@mail.alipay.com   → 支付宝账单
wechatpay@tencent.com     → 微信支付账单
webmaster@icbc.com.cn     → 工商银行（历史明细 PDF 也走邮件）
@icbc.com.cn              → 工商银行（域兜底，覆盖 noreply@ 等其他发信口）
```

匹配策略：**先按精确发件人命中**；再按**白名单域**命中；都未命中时用
「主题关键词 + 可信域名」兜底并标注"待确认"。

⚠️ **域名匹配必须按层级，不能按子串。**
`addr.endswith("icbc.com.cn")` 会把 `phish@icbc.com.cn.evil.com` 判成可信 ——
这是真实可利用的仿冒。正确写法只有两种：

```python
dom == pat  or  dom.endswith("." + pat)     # 完全相同，或真子域
```

`scripts/test_ledger_rules.py::test_sender_matching` 锁住了这条。

注意：`service@mail.alipay.com` 会发登录提醒，`webmaster@icbc.com.cn` 会发营销与安全提醒。
因此**白名单只决定"是否候选"**，真正取件时还要**按附件类型（`.zip/.csv/.xlsx/.pdf`）过滤** ——

## 八、工商银行历史明细 PDF（唯一的 PDF 来源）

标题：`中国工商银行借记账户历史明细（电子版）`，页脚有「第 N 页 / 共 M 页」。

**列头（11 列，从上到下在页面上是"从左到右"）：**

```
交易日期 | 账号 | 储种 | 序号 | 币种 | 钞汇 | 摘要 | 地区 | 收入/支出金额 | 余额 | 渠道
```

**值域（实测枚举）**
- `储种`：活期
- `币种`：人民币　`钞汇`：钞 / 汇
- `摘要`：理财 / 金融付款 / 消费 / 还款 / 转账 / 退款 / 跨境汇款 / 他行汇入 /
  工资 / 绩效 / 4月绩效 / 利息 / 费 —— **摘要不是分类**，是交易形态
- `渠道`：快捷支付 / 网上银行 / 手机银行 / 批量业务 / 其他
- `地区`：4 位数字机构码（如 `1202`）
- `收入/支出金额`：**自带正负号**（`+` 收 / `-` 支），是判方向的唯一依据
- `余额`：本行交易后的账户余额

**每页页脚（可直接当对账基准）：**

```
本页支出算术合计：123.45
本页收入算术合计：6,789.01
本页交易笔数：25
```

> 上面是**虚构示例值**（只保留真实的字段结构），仅用于说明页脚格式。
> 校验解析器时不要比对这些数字 —— 用 `ledger-model.md` 第八节的不变量。

**这份 PDF 的几何关系（最坑的地方，必须照抄）**

用 PyMuPDF `get_text("words")` 取到的 `(x0, y0)` 在这份文件里含义是**反的**：

| 维度 | 含义 | 量级 |
|---|---|---|
| `x0` | 沿表格**行**方向的位置（越大越靠下）| 行距 **7.0 ~ 8.0**，含页码/水印的杂行会插在中间 |
| `y0` | 沿表格**列**方向的位置（越大越靠表格**左**）| 列头 y0 从 713.27（交易日期）递减到 102.64（渠道）|

关键推论：

1. **`y0` 越小越靠表格右侧** —— 所以列带按 `y0` 升序排列时，列序是**反的**：
   第一列是「渠道」，最后一列是「交易日期」。把 bounds 和列头顺序直接配对，
   **每一列都会错位一格，金额与余额互换**，表现是明细全被丢掉（取不到金额格）。
2. **行内偏移最大 7.0，而行距也是 7.0** —— 两者同量级，
   **任何"按 x 自由聚簇"的做法都会裂行或串行**。
   正确做法：用**带符号金额格**当行锚点（每行恰好一个，水印里没有），
   取相邻锚点中点切行带。
3. **不要用「日期格」当锚点**：水印里也含 `2026-10-13` 这类日期戳，
   掺进来会把中位行距算成 7.5 而不是真实的 18，导致整行被切碎、每页少 3 笔。
4. 「摘要」列在实表里可能是**两个物理格**（如「绩效」+「7月工资及5月」），
   必须并成一格，否则整行列位右移。
5. 水印文字（申请单号尾段、收单流水号、「中国工商银行」、下单日期、下单时间）
   会**散布在表格的行间与列带之内**，所以归位之后还要**按内容过滤**
   （金额必须匹配 `^[+-][\d,]+\.\d{2}$`，余额必须匹配 `^[\d,]+\.\d{2}$`）。
   这些水印**每份文件都不同**（含申请单号/流水号），属于个人痕迹，不要写进随技能分发的文件。

**两个正交的对账校验（本格式的额外红利）**

- 逐页脚注：`本页交易笔数 / 本页收入算术合计 / 本页支出算术合计` 三项，逐页差额应为 0。
- **余额链**：按时间排序后 `本行余额 − 上行余额 == ±本行金额`。
  这是文件内部的强不变量，工行自己印在表里，比任何外部基准都硬。
